一切从最原始的问题开始：**怎样让两个玩家在同一个 3D 世界里看到对方移动？**

2026 年 6 月，GTS-Play 有了单机版本的 Demo，角色在场景里可以走路。但单机和多人的差距，不是"加个网络"那么简单。

第一个多人版叫 basic1，基于 Meta3D 引擎改造。目标很朴素：两个人进同一个房间，看到对方在走。

---

## 帧同步（Lockstep）—— 最直觉的想法

帧同步的思路很直接：**每个人把自己做了什么告诉所有人，各端各自算结果。**

```
每个逻辑帧：
  客户端 A → [命令] → 服务器 → 广播给所有客户端
  客户端 B → [命令] → 服务器 → 广播给所有客户端
  每个客户端收到所有人的命令 → 各自执行 → 状态理应一致
```

这套方案的最大好处是 **省带宽**——网络上传的不是状态（位置、血量），而是按键/操作指令。对于角色数量爆炸的游戏（星际争霸，上百个单位），帧同步几乎是唯一可行的方案。

但它的隐藏假设是：**所有客户端执行同样的命令，必须得出同样的结果。**

一个简单的 3D 移动逻辑：

```
if (按了A) 角色向左移动 speed 单位
```

帧同步要求这条逻辑在每个客户端、每次执行都产生完全相同的最终位置。听起来简单，实际上一旦牵涉到浮点运算：

- JavaScript 的 `Number`（IEEE 754 双精度浮点）在不同平台上精度表现不同
- Three.js 的 `Matrix4` 和 `Vector3` 运算在不同浏览器引擎上有微小差异
- 帧率变化 → 时间步长变化 → 浮点累积误差
- 碰撞检测用的 `Box3` 在不同精度下的边界判定不一致

**第一行代码还没写，就已经踩了三个坑。**

## basic1 的技术架构

下图是 basic1 的帧同步循环简化流程：

```
  ┌──────────────┐      ┌──────────────────┐
  │  Logic Loop   │─────▶│  Collect Commands │
  │  (15 FPS)     │      │  send AllCommands  │
  └──────┬───────┘      └────────┬─────────┘
         │                       │
         │                ┌──────▼──────┐
         │                │   Server    │
         │                │  broadcast  │
         │                └──────┬──────┘
         │                       │
  ┌──────▼───────────────────────▼──────────┐
  │  syncServer():                           │
  │    1. rollback predict data              │
  │    2. execute all server commands        │
  │    3. re-execute pending self commands   │
  └─────────────────────────────────────────┘
```

这套架构写在几个核心文件里：

**LogicManager.ts** 是整个帧同步的心脏。它的 `syncServer()` 方法处理服务器广播回来的命令：

1. **回滚（rollback）**：把之前的预测状态撤销，回到上一次确认的服务器状态
2. **执行服务端权威命令**：严格按照服务器返回的命令顺序执行一遍
3. **重新预测**：把自己已经发出但服务器还没确认的命令再执行一遍

我回忆一下这段代码的演化路径——AI 花了整整两天才把这套回滚逻辑写对。初始版本甚至没有回滚，直接叠加服务端命令，结果玩家位置反复跳变。

**MultiPlayerManager.ts** 负责客户端-服务端通信。它用 `logicLoop()` 以 15 FPS 定期收集当前帧的所有命令，打包发送给服务器；`renderLoop()` 用 `requestAnimationFrame` 以 60 FPS 做渲染。

注意这两个循环分离的设计——逻辑帧和渲染帧解耦。逻辑帧固定 15 FPS，渲染帧跑满显示器刷新率。每帧逻辑计算后，渲染层用插值（TWEEN）把动画过渡平滑。这是一个很经典的游戏引擎设计，但在 AI 编写的代码里能自然做出来，说明当初的提示词质量不错。

**Immutable.js 的介入**：所有多人状态都用 `Map`、`List` 管理，配合 `readState()` / `writeState()` 模式。每次状态变更都生成新对象，回滚时只需把指针指回旧状态。没有 Immutable.js，rollback + reapply 的复杂度会螺旋上升——改了一个引用类型，所有回滚逻辑全崩。

## 浮点数噩梦

这是帧同步最大的坑，没有之一。

场景很具体：两个玩家，客户端 A 和客户端 B，各自执行同一套命令序列，要求最终位置完全相同。

问题出在**加法不满足结合律**。JS 浮点数里：

```javascript
0.1 + 0.2 + 0.3  // 0.6000000000000001
0.3 + 0.2 + 0.1  // 0.6
```

两者不等。帧同步场景下，命令到达顺序可能不同→加法顺序不同→累积误差→位置不同步。

basic1 的解法是自己做了一套 `fNumber` 系统：

```typescript
// basic1/src/logic/math/FNumber.ts
type fNumber = number  // 包装类型，语义上表示"定点数"

export let add = (a: fNumber, b: fNumber) => { ... }
export let sub = (a: fNumber, b: fNumber) => { ... }
export let fromFloat = (n: number): fNumber => { ... }
export let toFloat = (n: fNumber): number => { ... }
```

本质上就是把浮点数用定点数编码，保证每次运算结果一致。但这也带来了额外复杂度——不能用原生 `+` `-`，所有运算都得过自定义函数。AI 特别容易忘记这层包装，直接写 `positionX += speed` 然后 debug 两小时。

## 碰撞检测的陷阱

basic1 的碰撞检测用的是 Three.js 的 `Box3`，跑在客户端。问题是：

- **客户端 A** 认为玩家在 (0.3, 0, 0)，碰撞了
- **客户端 B** 认为同一个人在 (0.30000001, 0, 0)，没碰撞

一个平台判定为碰撞导致位移被阻断，另一个平台没有碰撞继续移动。累积几个帧之后，两个客户端的场景天差地别。

这其实是浮点数问题的变体，但更隐蔽——碰撞是**开关逻辑**（碰/不碰），微小数值差异会触发完全不同的代码路径，不像位置差异还能平滑过渡。

## 帧同步 VS 状态同步

| 维度 | 帧同步（Lockstep） | 状态同步（Authoritative） |
|------|-------------------|------------------------|
| 服务器角色 | 命令中继 | 状态权威 |
| 客户端工作量 | 大（执行全量逻辑） | 小（只负责表现和输入） |
| 防作弊 | 弱（客户端有完整逻辑） | 强（服务器裁决一切） |
| 带宽 | 低（只传命令） | 高（传状态快照） |
| 浮点确定性 | ❌ 必须解决 | ✅ 不需要 |
| AI 编写难度 | 复杂（回滚+重放+插值） | 简单（客户端只管发输入） |
| 短板修复成本 | 高（所有端同步改） | 低（改服务端即可） |

## 瓶颈在哪

basic1 跑了大概 4 天。在它能用之后，团队很快遇到了天花板：

**1. 回滚代码的复杂度远超预期**

AI 写的 `syncServer()` 流程，边界条件特别容易出现 bug。比如：服务器返回的命令逻辑帧索引比客户端预测的还超前（网络快的时候），或者玩家下线后残留的命令还在帧缓冲里。每修一个 bug，回滚逻辑就多一层 `if`，逐步熵增。

**2. 调试极难**

帧同步出 bug 时，症状不在出 bug 的那台机器上，而是**别人的机器上**。你在自己电脑上看到角色瞬移了，原因可能在对面客户端的浮点精度问题。没有日志、没有复现手段，全靠猜。

**3. AI 的致命弱点**

帧同步要求全链路一致性——从浮点运算、碰撞检测、随机数生成到状态管理，每一个环节都不能有差异。AI 生成的代码天然带有小概率不一致（不同上下文生成的同一函数可能有细微区别），这种不一致在单机无所谓，在帧同步下是灾难。

---

## 为什么放弃

帧同步在理论上有它的吸引力——低带宽、高确定性、适合 RTS 和格斗游戏。

但在这个项目里，它带来的复杂度远超收益。

**关键认知转变：** 项目只有两个玩家，不是 8 个人的星际争霸。带宽不敏感，但代码可维护性高度敏感。在这个前提下，状态同步是更务实的选择——服务端做权威计算，客户端只管发输入和渲染结果。

状态同步意味着：服务器是老大，客户端是笨蛋。客户端永远不对最终状态做预测（除了 UI 手感上的本地预测），服务器每帧告诉客户端「你现在在哪、别人在哪」。这彻底解除了浮点确定性的紧箍咒——每个客户端独立插值，有点小误差无伤大雅。

basic1 的代码在后续重构中基本废弃（除了一些通信协议的思路），但它踩的每一个坑，都直接决定了 Phase 2 的技术选型。没有这 4 天的帧同步痛苦，就不会那么坚定地切换到状态同步。
