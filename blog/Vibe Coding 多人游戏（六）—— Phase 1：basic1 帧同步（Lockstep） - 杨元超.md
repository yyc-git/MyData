一切从最原始的问题开始：**怎样让两个玩家在同一个 3D 世界里看到对方移动？**

2026 年 6 月初，GTS-Play 开始做多人联机功能。单机版本「巨大娘的玩耍」已经是成熟的商业产品（v1.0，100k+ 行代码，30+ 版本迭代），角色在场景里可以走路、战斗、捕获。但单机和多人的差距，不是"加个网络"那么简单。

第一个多人原型叫 basic1。目标很朴素：两个玩家进同一个房间，看到对方在走。

---

## basic1：纯手写的第一版

basic1 是这条时间线上的**第一个里程碑，也是唯一一个完全由我手写的版本**——没有 AI 辅助，没有自动补全，一行行自己敲。

这个决定在当时是直觉性的：多人联网的逻辑太复杂了，我需要先自己搞清楚每一行是干什么的，才有资格让 AI 接手。

basic1 的技术栈：

- **Meta3D 引擎**（自研引擎）做场景渲染
- **Immutable.js** 做状态管理（为了支持回滚）
- **自定义 fNumber 定点数系统**（为了解决跨平台浮点一致性问题）
- **Node.js 裸写服务端**（没有框架，纯 TCP/WebSocket 手撸）

整个 basic1 的目录结构是我手动组织的，src 下 30+ 个文件，从 UI 到逻辑到渲染到网络通信，全在一个包里。

## 帧同步（Lockstep）—— 最直觉的想法

帧同步的思路很直接：**每个人把自己做了什么告诉所有人，各端各自算结果。**

```
每个逻辑帧：
  客户端 A → [命令] → 服务器 → 广播给所有客户端
  客户端 B → [命令] → 服务器 → 广播给所有客户端
  每个客户端收到所有人的命令 → 各自执行 → 状态理应一致
```

这套方案的最大好处是 **省带宽**——网络上传的不是状态（位置、血量），而是按键/操作指令。对于角色数量爆炸的游戏（星际争霸，上百个单位），帧同步几乎是唯一可行的方案。并且适合动作游戏，因为动作的计算在本地完成，延迟低。

但它的隐藏假设是：**所有客户端执行同样的命令，必须得出同样的结果。**

一个简单的 3D 移动逻辑：

```
if (按了A) 角色向左移动 speed 单位
```

帧同步要求这条逻辑在每个客户端、每次执行都产生完全相同的最终位置。听起来简单，实际上一旦牵涉到浮点运算：

- JavaScript 的 `Number`（IEEE 754 双精度浮点）在不同平台上精度表现不同
- Meta3D 引擎的矩阵运算在不同浏览器上有微小差异
- 帧率变化 → 时间步长变化 → 浮点累积误差
- 碰撞检测在不同精度下的边界判定不一致

**第一行代码还没写，就已经踩了三个坑。**

## basic1 的技术架构

下图是 basic1 的帧同步循环简化流程：

```
  ┌──────────────┐      ┌──────────────────┐
  │  Logic Loop   │─────▶│  Collect Commands │
  │  (15 FPS)     │      │  send AllCommands  │
  └──────┬───────┘      └────────┬─────────┘
         │                       │
         │                ┌──────▼──────┐
         │                │   Server    │
         │                │  broadcast  │
         │                └──────┬──────┘
         │                       │
  ┌──────▼───────────────────────▼──────────┐
  │  syncServer():                           │
  │    1. rollback predict data              │
  │    2. execute all server commands        │
  │    3. re-execute pending self commands   │
  └─────────────────────────────────────────┘
```

核心文件我手写了整整三天：

**LogicManager.ts** 是整个帧同步的心脏。`syncServer()` 方法处理服务器广播回来的命令，三步走：

1. **回滚（rollback）**：把之前的预测状态撤销，回到上一次确认的服务器状态
2. **执行服务端权威命令**：严格按照服务器返回的命令顺序执行一遍
3. **重新预测**：把自己已经发出但服务器还没确认的命令再执行一遍

**MultPlayerManager.ts** 负责客户端-服务端通信。用 `logicLoop()` 以 15 FPS 定期收集当前帧的所有命令打包发送；`renderLoop()` 用 `requestAnimationFrame` 以 60 FPS 做渲染。

逻辑帧和渲染帧分离的设计是我参考游戏引擎的做法手动写出来的——逻辑帧固定 15 FPS，渲染帧跑满显示器刷新率。每帧逻辑计算后，渲染层用 TWEEN 库把动画过渡平滑。

**Immutable.js 的介入**：所有多人状态都用 `Map`、`List` 管理。每次状态变更都生成新对象，回滚时只需把指针指回旧状态。没有 Immutable.js，rollback + reapply 的复杂度会螺旋上升——改了一个引用类型，所有回滚逻辑全崩。这个选择是我在写回滚代码到第三天时被逼出来的，最初用的是普通对象，回滚时深拷贝整棵树，性能直接爆炸。

## 浮点数噩梦：手写 fNumber

这是帧同步最大的坑，没有之一。我一个人 debug 了整整一个晚上才定位到这个问题。

场景很具体：两个玩家，客户端 A 和客户端 B，各自执行同一套命令序列，要求最终位置完全相同。

问题出在**加法不满足结合律**。JS 浮点数里：

```javascript
0.1 + 0.2 + 0.3  // 0.6000000000000001
0.3 + 0.2 + 0.1  // 0.6
```

两者不等。帧同步场景下，命令到达顺序可能不同→加法顺序不同→累积误差→位置不同步。

我的解法是自己写了一套 `fNumber` 定点数系统，放在 `basic1/src/logic/math/FNumber.ts` 里：

```typescript
type fNumber = number  // 语义上表示"定点数"

let add = (a: fNumber, b: fNumber) => { /* 定点数加法 */ }
let sub = (a: fNumber, b: fNumber) => { /* 定点数减法 */ }
let fromFloat = (n: number): fNumber => { /* 浮点转定点 */ }
let toFloat = (n: fNumber): number => { /* 定点转浮点 */ }
```

本质上就是把浮点数用定点数编码，保证每次运算结果一致。但这也带来了额外复杂度——不能用原生 `+` `-`，所有运算都得过自定义函数。后来 AI 写代码时经常忘记这层包装，直接写 `positionX += speed` 然后 debug 半天。

## 碰撞检测的陷阱

basic1 的碰撞检测用的是 Three.js 的 `Box3`，跑在客户端。问题是：

- **客户端 A** 认为玩家在 (0.3, 0, 0)，碰撞了
- **客户端 B** 认为同一个人在 (0.30000001, 0, 0)，没碰撞

一个平台判定为碰撞导致位移被阻断，另一个平台没有碰撞继续移动。累积几个帧之后，两个客户端的场景天差地别。

这其实是浮点数问题的变体，但更隐蔽——碰撞是**开关逻辑**（碰/不碰），微小数值差异会触发完全不同的代码路径。

## 帧同步 VS 状态同步

| 维度 | 帧同步（Lockstep） | 状态同步（Authoritative） |
|------|-------------------|------------------------|
| 服务器角色 | 命令中继 | 状态权威 |
| 客户端工作量 | 大（执行全量逻辑） | 小（只负责表现和输入） |
| 防作弊 | 弱（客户端有完整逻辑） | 强（服务器裁决一切） |
| 带宽 | 低（只传命令） | 高（传状态快照） |
| 浮点确定性 | ❌ 必须解决 | ✅ 不需要 |
| 手写难度 | 极高 | 中等 |
| 短板修复成本 | 高（所有端同步改） | 低（改服务端即可） |

## 瓶颈在哪

basic1 我手写了大概 4 天。在它能用之后，很快遇到了天花板：

**1. 回滚代码的复杂度远超预期**

`syncServer()` 的边界条件极其容易出 bug。比如：服务器返回的命令逻辑帧索引比客户端预测的还超前（网络快的时候），或者玩家下线后残留的命令还在帧缓冲里。每修一个 bug，回滚逻辑就多一层 `if`，逐步熵增。最崩溃的是有一晚修到凌晨两点，发现 bug 是因为一个 `Map.set()` 返回了错误的对象引用——Immutable.js 的 API 特性问题。

**2. 调试极难**

帧同步出 bug 时，症状不在出 bug 的那台机器上，而是**别人的机器上**。你在自己电脑上看到角色瞬移了，原因可能在对面客户端的浮点精度问题。没有日志、没有复现手段，全靠猜。

**3. 单人开发效率瓶颈**

一个人同时维护服务器、客户端、UI、网络协议、状态管理、碰撞检测——手写 30+ 文件。出任何一个 bug，排查链路都从"是我写错了还是设计问题"开始。

## 为什么放弃

帧同步在理论上有它的吸引力——低带宽、高确定性、适合 RTS 和格斗游戏。

但在这个项目里，它带来的复杂度远超收益。

**关键认知转变：** 项目只有两个玩家，不是 8 个人的星际争霸。带宽不敏感，但代码可维护性高度敏感。在这个前提下，状态同步是更务实的选择——服务端做权威计算，客户端只管发输入和渲染结果。**彻底的放弃帧同步，是在我手写 basic1 四天后做出的决定。**

状态同步意味着：服务器是老大，客户端是笨蛋。客户端永远不对最终状态做预测（除了 UI 手感上的本地预测），服务器每帧告诉客户端「你现在在哪、别人在哪」。这彻底解除了浮点确定性的紧箍咒——每个客户端独立插值，有点小误差无伤大雅。

basic1 的代码在后续重构中基本废弃，但它踩的每一个坑，都直接决定了 Phase 2 的技术选型。没有这 4 天的纯手写帧同步痛苦，后面引入 AI 时我根本不知道该怎么描述需求——知道「不要什么」和知道「要什么」同等重要。
