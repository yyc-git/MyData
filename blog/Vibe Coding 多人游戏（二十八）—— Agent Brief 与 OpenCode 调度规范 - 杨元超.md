OpenCode 调度中最关键的环节是写 **Brief**——给 AI 的任务说明书。Brief 写得好，AI 一次过；写得差，来回 5 轮 Bug 修复。

---

## Brief 结构

```
## 目标
一句话说清要做什么

## 背景
为什么要这么做（让 AI 理解上下文）

## 文件范围
明确列出改哪些文件、不改哪些

## 具体修改
分点列出要改什么（不是"怎么做"，是"改成什么样"）

## 不改的
明确边界——AI 越界最常见的原因就是边界没说清楚

## 红线
- 改 .ts 再 tsc，不改 .js
- 不改 node_modules
- 不改单机代码

## 测试
- 新增集成测试覆盖新逻辑
- 运行所有测试确保不 regression
```

---

## 体验式反馈 > 技术 spec

传统文档写的是"应该怎么做"（技术 spec），但 AI 更需要"为什么"（体验式反馈）。

```
❌ 技术 spec：
使用状态同步，服务端权威下发 position

✅ 体验式反馈：
当前问题：帧同步下 A 和 B 位置不一致
原因：浮点数精度各平台不同
目标：服务端算位置告诉客户端，客户端只展示
```

AI 理解了"为什么"后，自己会推导出"怎么做"——而且比我们告诉它更准确。

---

## 模型选择速查

| 任务类型 | 模型 | 原因 |
|---------|------|------|
| 新功能开发 | 付费 1M | 需要理解和生成大量代码 |
| Bug 修复 | 付费 1M | 需要追踪调用链 |
| 重构 | 付费 1M | 涉及多文件同步修改 |
| 小修小改 | 免费 200k | 改动小，Context 够 |
| 测试 | 免费 200k | 模式固定 |
| Code Review | 付费 1M | 需要理解大范围上下文 |
