AI 写代码很快，但**修 bug 是另一个故事**。

OpenCode 时代，AI 写代码 5 分钟，修 bug 可能 5 小时——特别是多人同步类的 bug，涉及前后端状态不一致，AI 经常越修越错。

---

## 传统 Debug 流程

AI 发现 bug 后，典型的修复流程：

```
AI：编译报错，让我看看日志
→ 读日志 → 觉得是问题 A → 改代码
→ 跑测试 → 还是报错
→ 觉得是问题 B → 改代码
→ 跑测试 → 又出新错
→ 无限循环...
```

**AI 修 bug 的通病：不结合日志定位，永远修不对。**

OpenCode 直接改代码而不看运行时的日志，就像蒙眼修车——能修好的概率基本靠蒙。

---

## E2E 自测设计

解决方案是**让 AI 能在真实环境中观测效果**：

```
1. 启动 room-service 和 match-service
2. 启动 Puppeteer/Playwright 打开两个浏览器窗口
3. 窗口 A 创建房间 → 窗口 B 加入
4. 窗口 A 移动 → 检查窗口 B 是否同步
5. 关掉窗口 A → 检查窗口 B 是否收到退房通知
6. 检查服务端日志有无异常
```

用两个浏览器窗口模拟两个玩家的行为，检查状态是否同步。如果 bug 真实存在，E2E 测试会失败，错误信息会暴露根因。

## 三天一个最难同步 Bug

GTS-Play 开发中最难的一个 bug：**玩家 A 在窗口 A 移动，窗口 B 中看到的是瞬移而非平滑移动。**

AI 花了 3 天定位：

1. **Day 1**：觉得是插值缓冲区没对齐 → 改插值逻辑 → 没解决
2. **Day 1 晚**：觉得是服务端 tick 频率太低 → 改 30fps → 稍微好点但本质问题还在
3. **Day 2**：觉得是 WS 消息乱序 → 加序列号检测 → 没有乱序
4. **Day 2 晚**：打印每 tick 状态发现——服务端下发的 position 和客户端收到的不一致
5. **Day 3**：根因是 `prepareBroadcastPlayers` 里剥离 OBB 数据时，做了一层深拷贝，但深拷贝函数没处理 Position 字段的浮点数精度

**最终修复：一行代码。**

但找到这一行花了 3 天。E2E 自测的意义就是让 AI 能自己走完这个过程，而不是人类盯着日志猜。

## 根因修复流程

E2E 自测发现问题后，修复流程应该是：

```
1. 复现 bug（E2E 测试天然做这件事）
2. 定位根因（看日志 → 缩小范围 → 看代码）
3. 写测试锁定 bug（红 → 绿）
4. 修复代码
5. 跑所有测试（确保没 regression）
6. 部署
```

其中第二步最关键——**AI 必须学会先看日志再改代码**。

OpenCode 的 `gts-dev-fix` Skill 被设计为：

```
1. 读 bug 描述
2. 搜相关代码
3. 看最近的日志（gts-logs）
4. 提出根因分析 → 让我确认
5. 我确认后开始修代码
6. 跑测试 → 循环直到通过
```

---

## 测试金字塔

最终测试体系分成三层：

```
     /\
    /E2E\          ← 双窗口模拟，手动触发
   /集成 \
  /测试   \        ← BDD 场景 + 自动验证
 /______\
/ 单元测试\       ← AI 自动写、自动跑
/________\
```

| 层 | 工具 | 执行者 | 覆盖率 |
|----|------|--------|--------|
| 单元测试 | Jest | AI 自动 | 核心逻辑 90%+ |
| 集成测试 | BDD Cucumber | AI 自动 | 服务端场景 7+ |
| E2E 测试 | Playwright | 手动触发 | 关键路径 |

**TDD 纪律：必须先让测试因 bug 真实失败，再修复。** 不准用 mock 函数绕过——mock 过的测试永远测不到真实路径。

---

## 验收自动化

`gts-acceptance` Skill 实现了验收的全自动化：

```
循环：改 → 测 → 验 → 通过 → 部署
```

每次循环：
1. OpenCode 修改代码
2. 编译检查
3. 运行集成测试（BDD）
4. 如果失败 → 查看日志 → 定位 → 继续改
5. 全部通过 → 自动部署

这个循环不会因为某次失败而卡死——每次失败都是人类看一眼 log 就能定位的问题，AI 自己也能处理大多数。
