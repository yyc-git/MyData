## 第一阶段：手动复制粘贴

2026 年 5 月，GTS-Play 刚起步时，开发流程是这样的：

```
1. 在 ChatGPT / Claude 上描述需求
2. AI 生成代码
3. 手动复制代码到编辑器
4. 手动运行 tsc 检查编译
5. 改 bug → 回到步骤 1
```

问题很明显：**循环太慢。** 生成代码 5 秒，复制粘贴 30 秒，编译检查 10 秒，发现 bug 再手动回到 AI 窗口重新描述——一个简单的函数改动要来回 5-6 次，每次手动操作。

更痛苦的是上下文丢失。AI 聊天窗口没有项目结构、没有类型定义、不知道你改到哪了。每次都要"把代码贴过去、描述需求、等生成、贴回来"。

**月费：~2000 元**（GPT-4 + Claude 3 Opus 轮着用）。

---

## 第二阶段：AI 编辑器（Cursor/Windsurf）

然后试了 Cursor 这类 AI 原生编辑器——编辑器直接和 AI 对话，能读取项目文件，不需要复制粘贴。

改进很大：AI 能看懂项目结构了。但问题还在：

1. **上下文窗口有限**：大项目里，Cursor 经常混淆不同文件的关系
2. **没有流程意识**：AI 不知道"改完代码要跑测试"、"跑完测试要部署"
3. **手动触发**：每次修改还是需要人工介入，做不到"改 → 测 → 修 → 再测"的闭环

用了两周，虽然比复制粘贴快，但离"自动化"还差得远。

---

## 第三阶段：OpenCode 接管终端

转折点是 **OpenCode**——一个终端里的 AI 编程 agent。

OpenCode 的核心理念：**AI 直接在终端里写代码、跑命令、看结果。**

```
user: "把 Move 命令改成支持凸包碰撞"

OpenCode:
  → 读取 packages/logic/src/logic/Movement.res
  → 分析当前凸包实现（SAT 分离轴定理）
  → 修改 executeCommand 集成凸包
  → 运行 rescript build
  → 发现类型错误 → 自动修复
  → 再次 rescript build → 通过
  → 运行 BDD 测试 → 通过
  → 输出修改总结
```

整个过程不需要人工介入。OpenCode 自己读文件、自己编译、自己修 bug、自己跑测试。

**关键变化：AI 不再是一个"建议者"，而是一个真正的"开发者"。** 它能看到编译器的输出、测试的失败信息、lint 的报错——和人类开发者看到的信息完全一样。

## 从 2000 元到 100 元

引入 OpenCode 之后，月费从 ~2000 元降到了不到 100 元。

为什么这么便宜？核心策略是**模型分层**：

| 任务 | 用什么模型 | 费用 |
|------|-----------|------|
| 代码生成、重构 | 付费模型（1M context） | ~0.15 元/次 |
| 调度、编排、plan | 免费模型（200k context） | 0 元 |
| 测试、lint、小修 | 免费模型 | 0 元 |

大部分 token 消耗在日常编译修复和测试上——这些完全不需要 GPT-4 级别的能力。免费模型做调度、付费模型做核心代码生成，分开后开销直接降到 1/20。

## 带来的文化变化

OpenCode 引入不仅省了钱，还改变了开发方式：

**1. 不再怕重构**

以前重构 = 手动改几十个文件，每个都要测试。现在重构 = 一句话描述目标，OpenCode 执行全程。

```
"把 executeCommand 从 switch-case 改成事件驱动模式"
→ OpenCode 自动修改所有调用点
→ 自动修复编译错误
→ 运行测试验证
```

**2. 小修小改不再烦躁**

以前改一个类型定义，要在 5 个文件里同步改。现在丢一句话，十秒完事。

**3. 代码质量反升**

AI 对一致性很敏感——你告诉它"所有 API 都用这种模式"，它就真的在所有新代码里用。不像人类偶尔会偷懒。

---

## OpenCode 的局限性

当然不是万能药：

1. **跑偏**：有时候 AI 理解错需求，写了一大堆不相干的内容（这就是后面要讲的 Skill 和 Brief 的作用）
2. **卡住不自知**：编译错误绕不过去时，AI 会卡在同一个地方反复尝试，需要外部检测超时
3. **没大局观**：单次修改 OK，跨多个 Package 的重构需要额外的上下文注入

后面两篇会讲怎么解决这些问题——OpenClaw 调度 + Skill 固化 + 自动部署。
